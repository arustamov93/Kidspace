# Payments Architecture & Billing System (Kidspace 5.0)

Этот документ описывает архитектуру платежного шлюза, интеграцию с провайдерами (UzCard/Humo через Payme/Click/Uzum), обработку подписок и транзакций KidsMarket.

---

## 1. Обзор архитектуры

Система использует гибридную модель:
1.  **Внутренний кошелек (Wallet):** Для микротранзакций (бронирование, разовые консультации). Позволяет избежать комиссий агрегаторов на частых мелких платежах.
2.  **Прямые платежи:** Для крупных покупок (Абонементы Kidspace Pass, корзина KidsMarket).
3.  **Рекуррентные платежи (Subscriptions):** Автоматические списания через токенизацию карт (Re-bills).

### Поддерживаемые провайдеры
*   **Payme / Click / Uzum:** Основные шлюзы для Узбекистана (UZS).
*   **Stripe:** Для международных карт (USD) - *Future Proof*.

---

## 2. Модель данных (Payment State Machine)

Каждый платеж проходит через строгий конечный автомат (State Machine) для обеспечения целостности данных.

### Статусы транзакции (`status`)
1.  **`CREATED`**: Инициализация намерения (Intent). Клиент нажал "Купить".
2.  **`PENDING_PROVIDER`**: Пользователь перенаправлен на шлюз (WebView/App).
3.  **`HOLD`** (Optional): Средства заморожены (для KidsMarket до подтверждения наличия).
4.  **`PAID`**: Провайдер подтвердил списание средств (через Webhook).
5.  **`COMPLETED`**: Бизнес-логика выполнена (Абонемент выдан, Заказ создан).
6.  **`FAILED`**: Ошибка оплаты или отмена пользователем.
7.  **`REFUNDED`**: Возврат средств.

---

## 3. Сценарии оплаты (Flows)

### A. Покупка Kidspace Pass (Direct Payment)

1.  **Client:** Вызывает `createPaymentIntent({ type: 'subscription', planId: 'pack_10' })`.
2.  **Server:**
    *   Создает документ в `payments` со статусом `CREATED`.
    *   Генерирует ссылку/форму для Payme/Click (с передачей `payment_id` в параметрах).
    *   Возвращает ссылку клиенту.
3.  **Client:** Открывает WebView или DeepLink платежной системы.
4.  **Provider:** Пользователь оплачивает. Провайдер шлет **Webhook** на наш сервер.
5.  **Server (Webhook):**
    *   Проверяет подпись запроса (Signature Validation).
    *   Находит транзакцию по ID.
    *   Проверяет сумму.
    *   Меняет статус на `PAID`.
    *   **Trigger:** Вызывает логику `activatePass(userId, planId)`.
    *   Меняет статус на `COMPLETED`.
    *   Отвечает провайдеру `{ result: OK }`.

### B. Рекуррентное продление (Auto-renewal)

Для этого требуется сохранение токена карты (Card Tokenization).

1.  **Первая оплата:** Проходит как в сценарии A, но с флагом `save_card=true`.
2.  **Сохранение:** После успеха Payme возвращает `card_token`. Мы сохраняем его в `users/{uid}/payment_methods` (encrypted).
3.  **Cron Job (Nightly):**
    *   Находит истекающие подписки.
    *   Вызывает API провайдера: `POST /receipts` с `card_token`.
    *   При успехе -> продлевает подписку.
    *   При неудаче (нет денег) -> шлет Push, пробует снова через 24ч (Retry Logic).

### C. Покупка в KidsMarket (Escrow / Hold)

1.  **Client:** Оформляет заказ.
2.  **Server:** Проводит транзакцию типа `HOLD`. Деньги списываются, но не перечисляются продавцу.
3.  **Logic:** Заказ собирается.
4.  **Delivery:** Курьер доставил товар -> Статус `DELIVERED`.
5.  **Server:** Переводит статус платежа в `COMPLETED`, средства зачисляются на баланс Партнера (за вычетом комиссии).

## 4. Интеграция провайдеров (Uzbekistan Specifics)

### Payme (Merchant API)
Payme использует протокол JSON-RPC. Мы должны реализовать единую точку входа (Cloud Function URL).

**Методы для реализации:**
1.  `CheckPerformTransaction`:
    *   Проверить, что товар/услуга доступны.
    *   Проверить сумму (защита от подмены цены).
    *   *Ответ:* `allow: true`.
2.  `CreateTransaction`:
    *   Проверить идемпотентность (не создан ли уже ID транзакции Payme).
    *   Зарезервировать транзакцию, перевести наш `payment` в состояние `PENDING_PROVIDER`.
3.  `PerformTransaction`:
    *   Фактическое списание.
    *   Перевести наш `payment` в `PAID`.
    *   Запустить бизнес-логику (выдача товара).
4.  `CancelTransaction`:
    *   Обработка возвратов. Если товар еще не выдан -> вернуть деньги.

### Click (Merchant API)
Использует `Prepare` и `Complete` этапы (POST запросы).

1.  `Prepare`:
    *   Валидация ID заказа и суммы.
    *   Вернуть статус `action=0` (Success).
2.  `Complete`:
    *   Подтверждение платежа.
    *   Проверка `merchant_trans_id`.
    *   Выполнение бизнес-логики.

## 5. Webhook Security & Idempotency

### Безопасность
*   **Basic Auth / Headers:** Click передает хеш (MD5/SHA1) параметров + Секретный ключ.
*   **IP Whitelisting:** Разрешать запросы только с IP-адресов серверов Payme/Click.
*   **Signature:** В каждой Cloud Function строго проверять подпись перед чтением тела запроса.

### Идемпотентность (Idempotency)
Сеть ненадежна. Провайдер может прислать вебхук `PerformTransaction` 5 раз подряд, если мы не ответили вовремя (тайм-аут).

**Решение:**
1.  В коллекции `payments` поле `provider_transaction_id` должно быть уникальным индексом.
2.  При получении вебхука:
    *   `ExistingTx = db.find({ provider_transaction_id })`
    *   Если `ExistingTx` уже `COMPLETED` -> Сразу вернуть `{ result: OK }` (не выполнять логику повторно!).
    *   Если `ExistingTx` в процессе -> Ждать или вернуть ошибку "In Progress".

## 6. Retry Logic & Reconciliation (Обработка сбоев)

Что если деньги списались, вебхук пришел, но наша БД упала/зависла при выдаче Абонемента?

### Уровень 1: Транзакции Firestore
Весь код вебхука обернут в `db.runTransaction`. Если бизнес-логика падает, статус платежа не сохраняется как `COMPLETED`.

### Уровень 2: Provider Retries
Если мы вернем 500 ошибку на вебхук, Payme/Click будут повторять запрос с интервалами (1 мин, 5 мин, 30 мин). Это штатное поведение.

### Уровень 3: Reconciliation Job (Сверка)
Cron Job запускается раз в час:
1.  Ищет платежи со статусом `PENDING_PROVIDER` старше 1 часа.
2.  Делает запрос к API Провайдера (`CheckTransaction` по ID).
3.  **Сценарий А:** Провайдер говорит "Оплачено".
    *   Мы принудительно запускаем логику выдачи товара.
    *   Обновляем статус на `COMPLETED`.
    *   Пишем алерт админу "Recovered lost payment".
4.  **Сценарий Б:** Провайдер говорит "Не найдено/Отменено".
    *   Переводим наш платеж в `FAILED`.
