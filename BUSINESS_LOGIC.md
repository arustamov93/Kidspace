# Business Logic & Module Flows - Kidspace 5.0

Этот документ описывает логику работы ключевых модулей, потоки данных, алгоритмы и реализацию в FlutterFlow/React.

---

## 1. Kidspace Pass & QR Scanning (Core Module)

**Описание:** Покупка абонемента и списание визитов через QR-код в заведениях.

### Flow Пользователя
1.  Пользователь выбирает пакет (например, "Active - 10 визитов") на странице `Pass`.
2.  Оплачивает через Кошелек/Click/Payme.
3.  Получает статус `active` и баланс визитов.
4.  Приходит в заведение, нажимает кнопку "Сканер".
5.  Сканирует QR-код заведения (содержит `institution_id`).
6.  Получает экран успеха: "Визит списан. Осталось: 9".

### Flow Системы
1.  **Покупка:**
    *   Проверка баланса кошелька.
    *   Создание документа в `kidspace_passes`.
    *   Обновление поля `current_kidspace_pass_id` в `users`.
2.  **Списание (Scan):**
    *   Получение `institution_id` из QR.
    *   Проверка статуса пасса (`active`) и баланса (`balance > 0`).
    *   Проверка валидности заведения (входит ли в пакет).
    *   **Transaction:** Уменьшение `balance` на 1, создание записи в `visits`.

### Алгоритмы и Ограничения
*   **Правило 30 минут:** Нельзя списать визит в *одном и том же* заведении чаще, чем раз в 30 минут (защита от случайных двойных списаний).
*   **Geo-Fencing (Опционально):** При сканировании проверять, что GPS пользователя совпадает с координатами заведения (радиус 500м).
*   **Expiry Logic:** Если `expiry_date` < `now`, пасс становится `expired`, списание невозможно.

### Автоматизация (Cloud Functions)
*   `onScanCreate`: Триггер на создание документа в `visits`. Отправляет Push-уведомление пользователю ("Списан 1 визит в RoboKids") и владельцу заведения.
*   `dailyPassCheck`: Scheduled job (раз в сутки). Ищет пассы, где `expiry_date` истек, меняет статус на `expired` и отправляет уведомление "Ваш пасс истек".

### FlutterFlow / Frontend Реализация
*   **Action Chain на кнопке "Купить":** Backend Call (Create Document `kidspace_passes`) -> Update App State (UserBalance) -> Navigate to Success.
*   **QR Widget:** Использует библиотеку сканера. `OnCodeScanned` -> Backend Call (Cloud Function `processVisit`). Не делать логику списания на клиенте для безопасности!

## 2. Directory & Booking (Каталог и Бронь)

**Описание:** Поиск, фильтрация и бронирование услуг (уроки, врачи, садики).

### Flow Пользователя
1.  Открывает каталог, выбирает фильтры (Район, Цена, Рейтинг).
2.  Выбирает услугу (например, "Пробный урок").
3.  Выбирает дату и время (слоты).
4.  Оплачивает депозит (если требуется).
5.  Получает тикет бронирования.

### Flow Системы
1.  **Поиск:** Query к коллекции `institutions` с фильтрами.
2.  **Бронирование:**
    *   Проверка доступности слота (в MVP можно упростить: просто запись, подтверждение менеджером).
    *   Создание документа `bookings` со статусом `pending` (если нужна оплата) или `confirmed` (если бесплатно).
    *   Если есть депозит -> вызов модуля Payments.

### Алгоритмы
*   **Ранжирование (Ranking):**
    1.  `isVerified` = true (партнеры выше).
    2.  `rating` (по убыванию).
    3.  `distance` (если есть доступ к геопозиции).
*   **Поиск по тексту:** Использование Algolia или простого `.where('keywords', 'array-contains', searchTerm)` для Firestore.

### Ошибки
*   "Слот уже занят" (Race condition). Решение: Firestore Transaction при создании брони.
*   "Недостаточно средств для депозита".

### Автоматизация
*   `onBookingCreate`: Отправляет уведомление партнеру (Email/Push/Telegram Bot).
*   `reminderJob`: За 2 часа до `date_time` отправляет пуш "Не забудьте про урок в 14:00".

## 3. Health+ (Телемедицина)

**Описание:** Подписка на врачей, чаты и видеозвонки.

### Flow Пользователя
1.  Пользователь оформляет подписку `Health Pass` или платит разово.
2.  Выбирает врача (фильтр "Online").
3.  Нажимает "Чат".
4.  Открывается комната чата (`chat_sessions`).
5.  Обмен сообщениями/фото.

### Flow Системы
1.  **Проверка доступа:** Перед открытием чата проверить `health_pass.isActive` ИЛИ наличие разовой оплаты.
2.  **Создание чата:**
    *   Проверить, есть ли уже чат с этим врачом. Если нет -> `create document chat_sessions`.
    *   Добавить участников `[user_id, doctor_id]`.
3.  **Отправка сообщения:** Добавить документ в подколлекцию `messages`. Обновить `last_message` и `unread_counts` в родительском документе чата.

### Ограничения
*   **Лимиты:** В базовой подписке 5 консультаций в месяц. При создании чата проверять `consultations_used < limit`.
*   **Приватность:** Медицинские данные (фото) должны храниться в защищенном бакете Storage (правила доступа только для участников чата).

### FlutterFlow Реализация
*   Использовать стандартный Chat Widget или ListView, привязанный к подколлекции `messages`.
*   Ordering: `timestamp` DESC.
*   Бесконечный скролл (Infinite Scroll) для истории.

## 4. Wallet & Payments (Финансы)

**Описание:** Единый баланс для всех покупок внутри экосистемы.

### Flow Пользователя
1.  Нажимает "Пополнить".
2.  Вводит сумму.
3.  Переходит на эквайринг (Click/Payme WebView).
4.  После успеха баланс обновляется.

### Flow Системы
1.  **Top-up:**
    *   Генерация ссылки на оплату.
    *   Webhook от провайдера (Click) -> Cloud Function.
    *   Cloud Function обновляет `users.wallet_balance` (+ сумма) и пишет лог в `payments`.
2.  **Внутренняя покупка:**
    *   Клиент вызывает Cloud Function `payForService`.
    *   Функция в транзакции: проверяет баланс, вычитает сумму, создает запись о покупке (Pass/Товар/Бронь).

### Ошибки
*   **Идемпотентность:** Обработка вебхука платежа дважды. Решение: хранить `transaction_id` провайдера и проверять его наличие перед начислением.

## 5. Marketplace (E-commerce)

**Описание:** Покупка товаров партнеров.

### Flow Пользователя
1.  Добавляет товары в `Local State` (Корзина).
2.  Нажимает "Оформить".
3.  Выбирает адрес доставки.
4.  Оплачивает с кошелька.

### Flow Системы
1.  **Checkout:**
    *   Принимает массив товаров `[{id, qty}]`.
    *   Проверяет наличие на складе (`stock_quantity`).
    *   Списывает деньги.
    *   Уменьшает сток.
    *   Создает `orders`.
    *   Очищает корзину.

### Автоматизация
*   `onOrderCreate`: Уведомление менеджеру склада/партнеру.

## 6. Admin Panel (Модерация)

**Описание:** Управление контентом.

### Действия Админа
1.  **Approve Review:** Админ читает отзыв (статус `moderation`), нажимает "Ок". Статус меняется на `published`. Рейтинг заведения пересчитывается.
2.  **Verify Institution:** Проверка документов, установка галочки `isVerified`.

### Cloud Function: `aggregateRatings`
*   Триггер: `onWrite` в коллекции `reviews`.
*   Логика: Если статус стал `published`, пересчитать средний рейтинг для `institution_id` и обновить поле `rating` в документе заведения. Это избавляет от сложных расчетов на клиенте.

## Сводная таблица правил Firestore (Security Rules)

| Коллекция | Read | Write | Примечание |
| :--- | :--- | :--- | :--- |
| `users` | Owner | Owner (partial) | Публичные поля (имя, аватар) доступны всем авторизованным. Баланс - только read. |
| `kidspace_passes` | Owner | Server Only | Клиент не может сам себе создать пасс или поменять баланс. Только через Cloud Functions. |
| `institutions` | Public | Admin/Owner | Владелец может править только свое заведение. |
| `reviews` | Public | Auth Users | Create разрешен. Update только своих (пока не опубликовано). |
| `chat_sessions` | Participants | Server/Participants | Читать могут только участники массива `participants`. |
| `admin_logs` | Admin | Server | Только для админов. |
